# Публикация лабораторной в GitHub

## Что уже сделано и что осталось

Владелец создал репозиторий [Alen0013/calibration-lab1](https://github.com/Alen0013/calibration-lab1).
На момент проверки, сохранённой в `reports/LAB1/github_status.json`, удалённая
ветка `main` содержит только первоначальный `README.md`. Код лабораторной,
подготовленные ветки и результаты ещё не опубликованы. Успешный GitHub Actions
run, слияние PR и защита `main` пока не подтверждены.

Попытка записи через подключённую интеграцию получила HTTP 403
`Resource not accessible by integration` и не изменила репозиторий. Пользователь
подтвердил вход GitHub CLI, но в среде подготовки проекта авторизация не
завершилась: сетевая политика заблокировала доступ к `api.github.com`.
Эти ограничения не затрагивают сохранённые локальные расчёты, отчёт и видео.

Для продолжения подготовлены `PUBLISH_GITHUB.bat` и
`scripts/publish_github.py`. **Сценарий ещё не исполнен на компьютере владельца.**
Его наличие и локальные проверки кода не являются доказательством публикации.

## Запуск на Windows

1. Установите Python 3.12 и Git. Для самого сценария публикации достаточно Python
   версии 3.10 или новее; приложение лабораторной рассчитано на Python 3.12.
2. Распакуйте полный архив проекта в обычную папку. В нём должны оставаться
   `PUBLISH_GITHUB.bat`, `scripts/publish_github.py` и `calibration_lab1.bundle`.
3. Дважды нажмите **`PUBLISH_GITHUB.bat`**. Файл запуска ищет `py -3.12`, затем
   `py -3`, затем `python`. Git должен быть установлен; сценарий сам его не устанавливает.
4. Если потребуется вход, завершите авторизацию GitHub CLI в открывшемся браузере
   на своём компьютере. Используйте аккаунт **Alen0013**. Пароль или токен не нужно
   копировать в чат или файлы проекта.
5. Дождитесь итогового сообщения. Во время проверки CI окно может оставаться
   открытым до пятнадцати минут. При остановке прочитайте причину и сохранённый
   результат, прежде чем повторять запуск.

Целевой репозиторий закреплён в сценарии:
`https://github.com/Alen0013/calibration-lab1`. Перед изменениями проверяются
владелец, идентификатор аккаунта и идентификатор репозитория. Этот файл запуска
не предназначен для публикации в произвольный другой репозиторий.

GitHub CLI используется из уже установленной копии либо скачивается из
официального релиза `cli/cli` в локальную папку инструментов. Для скачанного
архива сверяется SHA-256 по файлу контрольных сумм релиза. Авторизация проходит
обычным механизмом GitHub CLI на компьютере владельца.

Из терминала корня проекта доступен тот же запуск:

```powershell
python scripts/publish_github.py
```

Отдельная установка научных библиотек и запуск EDA для публикации не нужны.
Сценарий использует стандартную библиотеку Python, Git и GitHub CLI. При
нестандартном расположении bundle можно указать его явно:

```powershell
python scripts/publish_github.py --bundle "C:\Lab1\calibration_lab1.bundle" --ci-timeout 900
```

## Что выполняет сценарий

| Этап | Действие и проверяемый результат |
| --- | --- |
| Вход | Проверяет аккаунт GitHub и права работы с закреплённым репозиторием |
| Локальная история | Восстанавливает ветки из bundle в отдельную управляемую рабочую папку |
| Начальный README | Сохраняет историю уже созданного удалённого `main`, объединяя её с подготовленным `develop` |
| Публикация веток | Отправляет `develop` и подготовленные `feature/lab1-*` без force push |
| Pull request | Создаёт или использует PR из `develop` в удалённый `main` |
| GitHub Actions | Ожидает успешный workflow `ci.yml` для конкретного коммита, а не произвольный прежний зелёный запуск |
| Слияние | Сливает PR обычной командой с проверкой ожидаемого SHA, без административного обхода правил |
| Защита `main` | После слияния применяет подготовленные правила и читает их обратно с GitHub |
| Итог | Записывает фактически выполненные действия, ссылки и причину возможной остановки |

Локальный `main` из bundle напрямую не отправляется на GitHub. Удалённый `main`
изменяется только через слияние PR. Это сохраняет исходную историю репозитория
владельца. Неизвестное изменение удалённой истории приводит к остановке;
сценарий не заменяет её принудительной отправкой.

Если действующие правила уже требуют чужого одобрения, оно должно быть получено
от реального участника. Сценарий не создаёт отзыв от его имени, не использует
`--admin` и не переписывает уже установленную защиту ради слияния. Настройка
защиты и наличие PR сами по себе не подтверждают человеческое ревью.

## Где находится результат

Управляемая рабочая копия, инструменты и журналы сценария находятся в
`artifacts/` и исключены из Git.

| Путь | Содержание |
| --- | --- |
| `artifacts/github_publication.json` | Машиночитаемый результат попытки публикации |
| `artifacts/github_publication.log` | Журнал выполнявшихся этапов и сообщений |
| `artifacts/github-publish/clone/` | Отдельная рабочая копия, восстановленная из bundle |
| `artifacts/github-publish/managed_workspace.json` | Признак рабочей папки, созданной сценарием |
| `artifacts/github-publish/tools/` | Локальная копия GitHub CLI при необходимости скачивания |

После завершения откройте [репозиторий](https://github.com/Alen0013/calibration-lab1)
и сравните результат с журналом: в `main` должен появиться проект, PR должен быть
слит, Actions — содержать успешный запуск для опубликованного коммита. Факт
защиты подтверждается ответом GitHub, сохранённым при повторном чтении настроек.
Если один из этапов не завершён, не называйте весь процесс успешным.

`reports/LAB1/github_status.json` описывает состояние **на момент подготовки
комплекта**. Результат нового запуска находится в
`artifacts/github_publication.json`; исходный отчёт не становится автоматически
доказательством более поздней публикации. Для сдачи приложите ссылки и новый
результат к сохранённому отчёту.

## Если выполнение остановилось

Сначала прочитайте `artifacts/github_publication.log` и JSON-результат. Сценарий
не должен обходить отказ доступа, красный CI, требования ревью или неизвестные
изменения удалённой истории. Исправьте указанную причину и запустите тот же
`PUBLISH_GITHUB.bat` повторно. Уже созданные удалённые сущности проверяются перед
следующим действием; повторный запуск не означает безусловное повторное слияние.

При тайм-ауте CI проверьте вкладку Actions и состояние PR. При требовании ревью
попросите реального участника проверить работу. При неподдерживаемой или
недоступной защите ветки сохраните сообщение GitHub и укажите незавершённый этап
в материалах сдачи. Не удаляйте существующую удалённую историю и не выполняйте
force push для устранения такого сообщения.
